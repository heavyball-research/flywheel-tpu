# MLA block 拟合分档表 2：按离散分支重新拟合

这是 `docs/mla_block_heuristic_fit_table.md` 的第二版。数据仍然是已有的 649 个 cell，**没有重跑任何 kernel**。这一版先检查哪些输入是离散分组，再按分组重新拟合，最后给出新的分档表。

第三版（按 scenario × dtype 分支重新拟合）见 [`mla_block_heuristic_fit_table3.md`](./mla_block_heuristic_fit_table3.md)。
第四版（只分 scenario，按 VMEM / HBM 行为重写公式）见 [`mla_block_heuristic_fit_table4.md`](./mla_block_heuristic_fit_table4.md)。

## 1. 哪些维度是离散分组

cell 记录里的字段可以分成三类：

| 字段 | 取值数 | 性质 | 是否做分支 |
|---|---|---|---|
| scenario | 2（decode / verify） | 纯类别，互不相关 | **做分支** |
| kv_dtype | 2（bf16 / fp8） | 类别，但两种格式规律相近 | 不做全局分支 |
| heads | 4（16 / 32 / 64 / 128） | 有序数值 | 不做分支 |
| batch | 19 个整数值 | 有序数值 | 不做分支 |
| seq | 29 个整数值 | 有序数值 | 不做分支 |
| verify_tokens | 7 个整数值（decode 恒为 1） | 有序数值，进入 query rows | 不做分支 |
| decode_tokens | 4（8 / 32 / 64 / 128） | **计时循环的 decode step 数**，不是 kernel 配置输入 | 不做分支 |
| page_size | 1（恒为 1024） | 常量 | 不适用 |
| priority / tag / key / cache_gib / exists | — | 跑测试的元数据 | 不适用 |

结论：**真正需要分支的离散输入只有 scenario（decode / verify）**。dtype 虽然也是类别，但按你说的两种格式规律相近，这一版没有按 dtype 做全局拆分；只在 decode 的 fp8 小 batch 这个已知最差的局部做一个小门控。`decode_tokens` 容易被误认为分支，但它只是“一次计时里跑多少步 decode”，不参与 block/items 的计算。

## 2. 重新拟合后的分支

三个分支仍然共用一个公式骨架（`bound = next_pow2(S)`，block 按页对齐，items 取 2 的幂，VMEM 守卫不变），只改 items 上限：

| 分支 | 条件 | block 上限 | step token 目标 | items 上限 |
|---|---|---|---|---|
| 默认 | 其余所有情况 | 4096 | 8192 | 8 |
| decode · fp8 小 batch | scenario = decode，dtype = fp8，batch ≤ 16 | 4096 | 8192 | 2 |
| verify · 小 item 数 | scenario = verify，batch × ceil(S ÷ block) < 16 | 4096 | 8192 | 1 |

为什么是这两条分支：

- **decode · fp8 小 batch**：这一块是表 1 里误差最集中的地方。小 batch 时一步的总 token 少，items 堆到 8 反而拉长单步；把 items 上限降到 2，能修好 3 个复测确认的坏 cell（包括最严重的 15.6% 那个）。bf16 的小 batch 也有类似现象，但把同样的门控加到 bf16 上会产生更多新的复测坏 cell，所以只对 fp8 开这个门。
- **verify · 小 item 数**：verify 的 query rows 是 `heads × verify_tokens`，通常比 decode 大。当 `batch × ceil(S ÷ block) < 16` 时，一步里的总 item 数太少，最优做法是 **一步只放 1 个 item**，而不是缩小 block。表 1 里 verify 的坏 cell 几乎都是“demo 给 2 个 items、实测最优是 1 个”的情况；这条分支正好对上。
- **其余情况**：保持表 1 的默认参数。单独给 verify 拟合“缩小 block”的规则也试过：平均 regret 会再低一点，但会新增 3 个复测坏 cell，最后没有采用。

## 3. 分档结果

分档规则和表 1 相同：

| 档次 | 规则 | cell 数 | 占比 |
|---|---|---|---|
| **可用** | demo 就是实测最优或次优 | 267 | 41.1% |
| **基本可用** | 没进前二，但完整复测只慢 ≤5% | 97 | 14.9% |
| **未确认** | 没有完整复测，只有短测且短测只慢 ≤5% | 209 | 32.2% |
| **效果差** | 完整复测慢 >5%，或只有短测且短测慢 >5% | 76 | 11.7% |
| 合计 | | 649 | 100% |

和表 1 对比：

| 指标 | 表 1（单规则） | 表 2（分支） | 变化 |
|---|---|---|---|
| 可用 | 248 | 267 | +19 |
| 基本可用 | 103 | 97 | -6 |
| 未确认 | 215 | 209 | -6 |
| 效果差 | 83 | 76 | -7 |
| 复测确认的效果差 | 6 | 2 | -4 |
| 短测 regret 平均（全部 cell） | 2.46% | 2.29% | -0.17% |
| 复测 regret 平均（有复测的 cell） | 0.77% | 0.58% | -0.19% |

按组拆开：

| 组 | 可用 | 基本可用 | 未确认 | 效果差 | 合计 |
|---|---|---|---|---|---|
| decode · bf16 | 58 | 28 | 89 | 26 | 201 |
| decode · fp8 | 105 | 38 | 66 | 49 | 258 |
| verify · bf16 | 51 | 15 | 29 | 0 | 95 |
| verify · fp8 | 53 | 16 | 25 | 1 | 95 |

主要变化：

- **可用从 248 增加到 267，效果差从 83 减少到 76，复测确认的效果差从 6 减少到 2。**
- 短测平均 regret 从 2.46% 降到 2.29%，复测平均从 0.77% 降到 0.58%。
- 收益主要来自 verify 小 item 分支（修好 2 个复测坏 cell）和 decode fp8 小 batch 门控（修好 3 个，新增 1 个）。

剩下的 2 个复测确认坏 cell：

- `flywheel_mla-decode-h32-s2048-p1024-kvfloat8_e4m3fn-b8-n128`：最优 512/8，demo 2048/2，复测慢 8.4%
- `flywheel_mla-decode-h32-s3584-p1024-kvfloat8_e4m3fn-b2-n128`：最优 512/8，demo 4096/2，复测慢 7.0%

这两个都是小 batch decode fp8、且实测最优是 `512/8` 的 cell。它们的共同点是“最优配置比公式给出的 block 小很多”，属于表 1 就指出的锯齿悬崖；简单分支修不了，除非再开一个更窄的例外分支或补测。
