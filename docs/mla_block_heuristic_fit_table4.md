# MLA block 拟合分档表 4：只分 scenario，按 VMEM / HBM 行为重写公式

这是分档表的第四版。按你的要求，只保留 **decode / verify 两个分支**；但这次不是只换常数，而是改了公式结构：用“每步 KV 字节数”和“verify 的 score 临时区”来决定 block 和 items。数据仍然是已有的 649 个 cell，**没有重跑任何 kernel**。

## 1. 规则

先把几个词说清楚：

- **block**：一个 item 覆盖的 KV 长度（token 数）。
- **items**：一个 pipeline step 同时处理多少个 item。
- **VMEM**：TPU 片上的小块高速 SRAM，kernel 的 KV ring、query ring、score 临时区都放这里。
- **HBM**：KV cache 所在的高带宽内存。block/items 的选择，本质是在“HBM 一次搬多少”和“VMEM 放不放得下”之间取舍。

共用部分：

```
每 token 字节数 rowbytes = 640 × itemsize        # bf16: 2, fp8: 1
上界 bound = max(512, next_pow2(S))
总 item 数 A = B × ceil(S / block)
每步 KV 字节预算 STEP = 5 MiB
```

两条分支：

```
decode（HBM 吞吐为主，VMEM 不紧）
  block 上限 = STEP ÷ rowbytes                 # bf16 4096, fp8 8192
  block = mla_block_kv(page, ceil(S/page), min(bound, block 上限))
  step = STEP ÷ rowbytes
  items 上限 = 4
  若 A ≥ 64 × itemsize:                        # 独立 item 足够多，流水加深
      step = 2 × step
      items 上限 = 8
  items = 最大的 2 的幂 ≤ min(items 上限, step ÷ block, 16384 ÷ block, A)
  VMEM 保护：先减 items；仍超就 block 减半（和现有 kernel 相同）

verify（score 临时区是主要矛盾）
  min_items = max(1, 2 ÷ itemsize)             # bf16 1, fp8 2
  step = STEP ÷ rowbytes                        # bf16 4096 token, fp8 8192 token
  block 上限 = step ÷ min_items                 # 两种 dtype 都是 4096 token
  block = mla_block_kv(page, ceil(S/page), min(bound, block 上限))
  items = 最大的 2 的幂 ≤ min(2, step ÷ block, 16384 ÷ block, A)
  软预算 = 0.75 × kernel 的 VMEM 预算
  若 VMEM(block, items) > 软预算：block 减半，重算 items（保持流水深度），不要先砍 items
```

`16384 ÷ block` 这一项只是为了让输出配置落在 tuner 测过的范围内，不是硬件约束。

## 2. 数据里看到的三个关系

### 2.1 每步 KV 字节数跨 dtype 不变

按完整复测的最优配置统计，一步的 `block × items` 分布是：

| dtype | 最优配置的每步 token 数（四分位） | 折算成 KV 字节 |
|---|---|---|
| bf16 | 4096 / 4096 / 8192（p25 / 中位 / p75） | 5.24 / 5.24 / 10.5 MB |
| fp8 | 4096 / 8192 / 16384 | 2.62 / 5.24 / 10.5 MB |

**按字节看，两种 dtype 的中位数都是 5.24 MB**。bf16 的 4096 token 和 fp8 的 8192 token 是同一条等字节线。所以公式里不该出现“bf16 用 4096、fp8 用 8192”这种分支，直接写 `5 MiB ÷ 每 token 字节数` 就会自动得到两者。

decode 的最优形状也沿这条线：bf16 常见 `(512, 8)`、`(1024, 4)`、`(2048, 2)`、`(4096, 1)`，乘积都是 4096 token；fp8 常见 `(1024, 8)`、`(2048, 4)`、`(4096, 2)`、`(8192, 1)`，乘积都是 8192 token。大 batch 时整条线翻倍到 10.5 MB（bf16 8192 token、fp8 16384 token）。

### 2.2 decode：VMEM 很松，瓶颈在 HBM

decode 的最优配置只用了 VMEM 预算的 17–33%（中位数 bf16 25%、fp8 17%）。也就是说 decode 不是“放不下”，而是“每步搬多少 KV 最划算”。所以 decode 的公式只需要控制每步字节数和流水深度：

- 每步 5 MiB 是主体；
- 当 `A ≥ 64 × itemsize`（bf16 约 128 个 item、fp8 约 64 个）时，独立 HBM 请求已经足够多，把一步翻倍到 10 MiB 能更好地摊薄每条请求的固定开销；
- fp8 的 item 只有一半字节，所以它更早进入“大 batch”区间，这就是阈值乘 `itemsize` 的原因。

### 2.3 verify：score 临时区才是瓶颈，VMEM 不够时应该减 block

verify 的 query 行数是 `tokens × heads`，可以到 1024 行。score 临时区的大小近似是：

score 字节 ≈ 同时存活的 item 数 × query 行数 × block × (4 + itemsize)

大行数时，verify 的最优配置会用掉 43–93% 的 VMEM 预算；decode 只有 17–33%。这解释了 verify 的一个关键现象：

- fp8、1024 query 行、S = 16384 时，`(8192, 1)` 的 VMEM 也放得下，但实测比最优慢约 18–19%；
- 最优是 `(2048, 2)` 或 `(2048, 4)`：block 更小、items 更多。

原因是 block 减半时 score 临时区也减半，而 items 从 1 加到 2 只让“同时存活的 item 数”从 1 加到 2，流水还更深。**所以 verify 的正确做法是：VMEM 不够时减 block、保住 items；而不是像现在的 kernel 那样先砍 items。** 表 3 的 verify·fp8 分支其实也是在手工模拟这件事，这一版把它写成了公式。

`min_items = 2 ÷ itemsize` 的含义是“每 token 的 KV 至少凑够约 2 字节的流水深度”：bf16 一个 item 就是 2 字节/token，所以 1 个够；fp8 一个 item 只有 1 字节/token，所以至少要 2 个。这样 bf16 / fp8 的差异由字节数自动产生，不需要 dtype 分支。

## 3. 结果

分档规则和之前相同：

| 档次 | 规则 |
|---|---|
| 可用 | 启发式就是实测最优或次优 |
| 基本可用 | 没进前二，但完整复测只慢 ≤5% |
| 未确认 | 没有完整复测，只有短测且短测只慢 ≤5% |
| 效果差 | 完整复测慢 >5%，或只有短测且短测慢 >5% |

主要结论：

- **只分 scenario 的 359 个可用，已经几乎追平五分支持的表 3（362 个）**，比表 2 的 267 个多 92 个。
- **短测平均 regret 2.10%，和表 3 的 2.10% 持平**；复测平均 0.47%，比表 3 的 0.48% 略低。
- 复测确认的效果差是 3 个（表 3 是 2 个），全部在 decode·fp8 的小 batch、h32 角落。

剩下的 3 个复测确认坏 cell：

- `flywheel_mla-decode-h32-s1024-p1024-kvfloat8_e4m3fn-b8-n128`：最优 1024/1，启发式 1024/4，复测慢 16.5%
- `flywheel_mla-decode-h32-s3584-p1024-kvfloat8_e4m3fn-b2-n128`：最优 512/8，启发式 4096/2，复测慢 7.0%
- `flywheel_mla-decode-h32-s2048-p1024-kvfloat8_e4m3fn-b14-n128`：最优 2048/2，启发式 2048/4，复测慢 5.9%

verify 还有 2 个只有短测数据、短测慢 >5% 的 cell：

- `flywheel_mla-verify-h128-s4096-p1024-kvfloat8_e4m3fn-b8-t5-n8`：最优 2048/2，启发式 4096/2，短测慢 12.9%
- `flywheel_mla-verify-h128-s4096-p1024-kvfloat8_e4m3fn-b8-t6-n8`：最优 2048/2，启发式 4096/2，短测慢 6.4%

这 2 个都是 fp8 verify、h128、S = 4096、batch 8，启发式给 `(4096, 2)`，短测最优是 `(2048, 2)`。完整复测里没有它们，所以没有升级成“确认坏”。再继续加规则就只是对这几个 h32/h128 角落做硬编码了。

需要说明的是：5 MiB、64 × itemsize、0.75 的软预算、最小深度 2 这些常数，都是在同一批 649 个 cell 上拟合出来的，属于 **in-sample**；公式的**形式**来自 VMEM / HBM 的行为，但常数换到没测过的形状上不一定全部成立。
