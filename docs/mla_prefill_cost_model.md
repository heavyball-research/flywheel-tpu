# MLA prefill 的块代价模型

`default_mla_prefill_config` 用这个模型选一次 prefill 调用的
`(block_q, block_kv, row_groups)`。TPU v6e + bfloat16 cache 已启用；没有标定条目的
chip / dtype 退回旧的 `max_seqlen` 规则（并警告一次，`CALIBRATION` 为空时不警告）。

## 术语

- `block_q`：一个 q 块覆盖多少条 query token；kernel 按 q 块循环。
- `block_kv`：一个 KV item 覆盖多少列 key/value；kernel 再按 item 循环。
- `row_groups`：把 q 块的 `block_q × H` 行切成几组并行处理，H 是 head 数（这里 32）。
- `group_rows`：每组实际的行数，`group_rows = (block_q / row_groups) × H`。同一个
  `group_rows` 可以由不同 `(block_q, row_groups)` 得到，模型只用它的实测效率因子。
- VMEM：TPU 的片上向量内存。配置的 KV 环、query staging、状态和 score 缓冲都必须放进
  预算（取 VMEM 上限的 0.75），放不进就不是候选。
- 遗憾（regret）：所选配置的实测时间 / 该负载实测最快配置的时间 − 1。判据是每个
  验证组的遗憾都不超过 2%。

## 公式

一次调用的静态形状给出 batch B、总 query token 数 T、最长 chunk Qmax、最长上下文
Kmax、页宽 page 和容量 capacity。模型先用长度先验把它展开成若干 (q, n) 样本（见下一节），
再对每个候选配置计算期望时间：

C(config) = p(block_q) · h(group_rows) · e(block_kv) · W
         + c_blocks · blocks + c_rows · rows
         + c_qcopy · q_tokens + c_item_rows · item_rows

- W = Σ block_q · H · cols，cols 是 kernel 实际计算的 key 列数；
- blocks = Σ ceil(q / block_q)，是一个调用里的 q 块总数；
- rows = Σ block_q，q_tokens = Σ q_count · H；
- item_rows = Σ m · block_q · H，m 是一个 q 块里的 item 数；
- p、h、e 是实测效率因子，p(128) = 1、h(256) = 1；e 是每计算一个 score 元素
  （一条 query × 一个 head × 一列 key）的代价，W 已经把 block_q、H 和列数乘进去。

因子分开是因为 v6e 上它们可以分别测出来：只改宽度或只改行分组、列数完全不变时，
时间仍然会变。

每个 q 块的第 j 个 item 覆盖的 key 范围：

F = n − q + j · block_q
E = F + q_count
m = max(ceil(E / block_kv), 1)

前 m − 1 个 item 是满块，算 block_kv 列；最后一个 item 只在
block_kv 是 256 的整数倍且大于 256 时走 live-tile 路径，只算
256 · ceil(span / 256) 列，span = E − (m − 1) · block_kv；否则仍按满块算。
当 block_kv 是 256 的整数倍时，这个规则等价于整个 q 块只算
256 · ceil(E / 256) 列，所以在候选的大块之间（都是 256 的整数倍）改大改小不改变 W，
只改变 item 数和每个 item 的固定开销；模型就是靠这两项区分 512、768、1024 的。

## 长度先验

先验直接复用 MLA decode 的 `WORKLOAD_PRIOR`：12 支 = 3 个尺度 × 4 种形状
（uniform / spiky / longtail / pareto），每支取 8 个等质量分位点。对一个调用只解一个
尺度 s，用 80 步二分使

E[min(s · w, Qmax)] = T / B

然后

q = min(s · w, Qmax)
n = min(s · w, Kmax, capacity)，且 n ≥ q

样本的权重之和为 1，结果是确定的。这样平均 chunk 比 Qmax 短时会混合“整段 prompt”
和“只来了一部分 chunk”的请求；当每个请求都是满 chunk 时，上下文长度会一直铺到 Kmax。
先验是部署假设，不是拟合参数；拿到线上真实长度分布后应替换 `WORKLOAD_PRIOR`，
而不是按验证集调权重。

## 合法候选集与剪枝

- `block_kv` 必须和页对齐：`block_kv % page == 0` 或 `page % block_kv == 0`，
  且不超过 `min(2048, next_pow2(min(Kmax, capacity)))`。页宽只改变哪些块合法，
  不改变同一个配置的实测时间（page 128 和 512 的同配置差异在 0.7% 以内，
  page 256/1024 的单点也与 512 一致）。
- 常数表列出的 block（128..2048，每 128 一档）才是候选；没测过的块不用 1.0 占位价。
- 宽度取实测过的 32 / 64 / 96 / 128 / 192 / 256；`block_kv ≥ 1024` 时只留
  128 / 256（其它宽度不是 128 行 lane tile 的整数倍，实测慢 27% 到 2.5 倍）。
- 宽度上限：`block_q = 256` 只到 `block_kv = 512`，`block_q = 192` 只到 640。
  实测 256 在 640 / 768 比 512 慢 2.7 / 2.8 倍；192 在 640 只慢 1.2 倍，但在
  768 / 896 慢 2.4 / 2.5 倍。它们的慢 cell 也不进拟合。
- 行分组取 64 / 128 / 256 / 512 / 1024。每个 `(block_q, block_kv)` 先按 VMEM 预算
  过滤，再只保留效率因子最小的可行分组。256 在剪枝后的整个格上都可行且因子最小
  （h(256) = 1），所以实际选中总是 `group_rows = 256`；256 不可行时才退到更大的分组。
- 代价最小的配置胜出；平局取更长的 `block_kv`，再取更宽的 `block_q`。
- 宽度还受 `next_pow2(Qmax)` 限制：短 chunk 的 batch 不会去定价它填不满的 q 块。

## 实测（TPU v6e，bfloat16）

每个 cell 用 3 次 warmup + 5 次计时，取 5 个样本的中位数；VMEM 超预算的 cell 跳过。
拟合数据共 103 个 cell，来自 10 个 (page, q_lens, kv_lens) 负载组（page
128/256/512/1024，q_len = kv_len 的整段 prompt，以及 q_len < kv_len 的 chunked
prefill，长度覆盖 512 到 16384）。

e(block_kv)（单位 1e-9 ms / score 元素）：

| K | 128 | 256 | 384 | 512 | 640 | 768 | 896 | 1024 | 1152 | 1280 | 1408 | 1536 | 1664 | 1792 | 1920 | 2048 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| e | 0 | 0.182 | 1.668 | 1.430 | 2.205 | 1.778 | 2.356 | 2.075 | 2.451 | 2.856 | 2.544 | 6.731 | 5.919 | 6.520 | 5.930 | 5.948 |

两个悬崖决定了剪枝：

- `block_kv` 1536 / 2048 的 e 约是 1024 的 3 倍。q = kv = 8192、batch 2 的
  bq128 实测：K1024 6.86 ms，K1536 16.00 ms，K2048 14.19 ms。再往上也不恢复：
  K2560 / 3072 / 3584 / 4096 是 13.50 / 12.70 / 12.18 / 11.64 ms，仍远慢于
  K1024，所以最大 block 定在 2048，且 1536..2048 留在表里如实定价。
- 宽度悬崖见上一节；`block_q = 128` 的 K512 / 768 / 1024 都在 7 ms 量级，
  是长上下文的主力。

行分组的实测（同一 workload、bq、K 下比较）：

- `group_rows = 256` 在 8 个多分组 cell 里 7 个最快，另 1 个与最快打平（差 0.1%）；
- 128 有 codegen 路径问题：c_long16k 的 bq128/K1024 上 44.57 ms，同 cell 的 256 只要
  13.33 ms；所以 128 的 fit cell 全部剔除，表里按干净的 K512 比例 1.31 定价；
- 64 慢 2.5 到 5.6 倍；512 / 1024 中位慢 3.5% / 3.5%，最坏 6.1% / 7.5%。

`group_rows = 256` 的 103 个 cell 上，拟合的平均相对误差 3.51%、最大 12.66%；
用拟合值在同一批 cell 上做选择，最大分组遗憾 1.76%（u8192p128 选 K768，比实测最优的
K1024 慢 1.76%；其它组选中实测最优）。这是样本内数字，不是判据；判据是下面独立的
验证集。

## 标定与拟合

拟合把公式拆成三块交替求解：

1. 线性项和 e(K)：固定 p、h，用非负最小二乘（NNLS）解相对误差目标；
2. h(group_rows)：固定其它项，按测量时间加权最小二乘，并固定 h(256) = 1；
3. p(block_q)：同样加权最小二乘，固定 p(128) = 1。

重复 12 轮。只用 `group_rows = 256` 的 cell 拟合线性项、e 和 p，因为选择总是取 256，
要拟合的正是这个决策面；h 的其余值取实测干净比例。VMEM 跳过的 cell、宽度悬崖外的
cell、K > 2048 的 cell、以及 group_rows = 128 的病态 cell 都不参与线性拟合。

## 验证

验证集是与标定不同的 4 个负载（不同页宽、batch、长度形状；seed 固定）：

| 负载 | page | batch | q_lens | kv_lens | 选择 | 最优 | 所选 ms | 最优 ms | 遗憾 |
|---|---|---|---|---|---|---|---|---|---|
| v_uniform2k_p128 | 128 | 8 | 2048 × 8 | 2048 × 8 | bq128/K768/rg16 | bq128/K1024/rg16 | 2.1426 | 2.1269 | 0.74% |
| v_spiky16k_p1024 | 1024 | 4 | 2048,2048,1024,512 | 16384,8192,4096,2048 | bq128/K1024/rg16 | 同选 | 5.0261 | 5.0261 | 0.00% |
| v_longtail32k_p512 | 512 | 2 | 2048,512 | 32768,4096 | bq128/K1024/rg16 | 同选 | 6.5436 | 6.5436 | 0.00% |
| v_pareto8k_p512 | 512 | 4 | 2048,1024,512,512 | 8192,4096,2048,1024 | bq128/K1024/rg16 | 同选 | 1.9852 | 1.9852 | 0.00% |

表里 bq / K / rg 分别指 block_q / block_kv / row_groups。547 个 cell 全部成功。
平均遗憾 0.19%，最大 0.74%，每组都在 2% 以内。同样四个
负载上旧的 `max_seqlen` 规则（bq128/K512）的遗憾是 1.90% / 4.61% / 4.32% / 5.53%。
bq256/K512 在三个负载里是第二名（v_uniform2k 上只慢 0.03%）。被剪枝的配置
都作为 spot check 测了：256@640/768 和 192@1024 最慢，用时是各自最优的 2.4 到 2.7 倍；
160/224/240@512 里最快的是 v_longtail 的 160@512，也只排第 9/107，比最优慢 5.5%。
所以剪枝没有藏住更快的配置。

oracle 不是启发式自己的候选集，而是每个负载的全部合法 cell：所有页合法的
`block_kv` × 实测宽度 × 5 个实测行分组；K ≥ 1024 时的宽度取实测的 128/256。
被剪枝的配置作为 spot check 加回来：page 128 上的 256@640 / 768，每个负载的
192@1024，以及不属于候选域的 160 / 224 / 240 宽度在 512 上的 cell，共 547 个。启发式选中的
配置先在 oracle 里定位，再和该组的实测最快 cell 比较；被剪枝的配置也算在遗憾里。

## 当前状态与限制

- `CALIBRATION["TPU v6e"]["bfloat16"]` 已填入上面的常数，默认路径优先使用它；
  没有标定条目的 chip / dtype 仍用旧规则。
- 在 4 个独立负载、547 个 oracle cell 上，标定启发式的最坏遗憾 0.74%、平均 0.19%，
  满足“每组不超过 2%”的判据；同一验证集上旧的 `max_seqlen` 规则最坏 5.53%。
- 标定在一张 v6e 上完成（`vmem_limit_bytes()` 取 100 MiB，候选预算为其 0.75；
  bf16 cache）。换 chip、换编译器或换 cache dtype 不能直接复用这组数，应重跑标定并
  新增 `CALIBRATION` 条目。
- K > 2048 被排除，因为实测不恢复；若将来 kernel 修好长块路径，需要重新测量。
- 先验决定“平均而言”最优的配置。真实流量如果和 `WORKLOAD_PRIOR` 差很多，应替换先验；
  单个已知 (q_len, kv_len) 分布的工作负载可以用该分布直接做先验样本。
